# 건틀릿 모드 (계단 아레나) — 설계

길쭉한 판형 아레나가 계단으로 이어지고, 각 계단에 몬스터가 대기합니다. 플레이어가 출발시킨
공룡들이 계단을 하나씩 올라가며 싸우고, 마지막 계단에는 보스가 있습니다. 공룡이 전멸하면
버튼을 눌러 다음 무리를 출발시킵니다. 위로 갈수록 어려워집니다.

기존 대전 모드와는 **배치 화면 상단의 토글**로 전환합니다.

---

## 0. 규모

**계단은 총 10개입니다.** 각 계단의 몬스터는 올라갈수록 **더 세지거나 더 많아집니다** — 두
손잡이를 다 씁니다 (3.2의 사다리 표).

계단 수와 층별 마릿수는 둘 다 `GauntletLadder` 애셋의 데이터입니다. 코드 상수가 아니므로
10층을 12층으로 바꾸는 것은 애셋 편집이지 재설계가 아닙니다.

> 초안에서 이 문장을 "계단마다 몬스터 10마리"로 잘못 읽었습니다. 소유자 확인으로 정정.
> 남겨두는 이유는 마릿수 곡선이 이 정정 때문에 생긴 것이기 때문입니다 — 층마다 10마리
> 고정이었다면 "많아짐" 손잡이 자체가 없었습니다.

## 1. 지금 구조에서 깨지는 것

이 섹션이 이 문서에서 제일 중요합니다. **설계보다 먼저 읽으세요** — 아래 7개 중 첫 번째를
해결하지 못하면 나머지 설계는 전부 무의미합니다.

### 1.1 공룡은 계단을 못 올라갑니다 ⚠️ 최대 위험

`CreatureLocomotion.ApplySteering()` (`:148`):

```csharp
Vector3 change = new(desiredVelocity.x - current.x, 0f, desiredVelocity.z - current.z);
body.AddForce(Vector3.ClampMagnitude(change, moveSpeed) * acceleration, ForceMode.Acceleration);
```

- **수직 성분이 없습니다.** y는 항상 0입니다. 추진력은 전부 수평이고, 높이는 중력과 콜라이더가
  지형을 타고 넘는 것에만 의존합니다.
- 바로 위에 `if (!IsGrounded) return;` 이 있습니다. 접지 판정이 끊기면 **조향이 통째로 멈춥니다.**
- `IsGrounded` 는 `transform.position + up*0.1` 에서 아래로 1.3유닛 레이캐스트입니다.
- **물리 콜라이더는 의도적으로 작습니다** — 보이는 몸의 약 1/4 (`CreatureImpact` 주석 참고).
  캡슐이 작을수록 넘을 수 있는 단차도 작아집니다.
- `NavMesh 미사용` 은 명시된 설계 결정입니다 (`CLAUDE.md`).

즉 **말 그대로의 계단(수직 면)은 물리적으로 못 올라갑니다.** 랩터는 0.3유닛 턱에도 걸릴 수
있습니다. 이건 튜닝 문제가 아니라 구조 문제입니다.

### 1.2 aggroRange 90 — 1층 공룡이 10층 보스를 노립니다

실제 값은 **90**입니다. C# 기본값은 80이지만 (`CreatureDefinition:45`)
`SampleContentBuilder:101` 이 생성하는 모든 애셋에서 `definition.aggroRange = 90f` 로
덮어씁니다. 아레나 반지름은 **22**이므로 지금까지는 "아레나 전체"라는 뜻이었고 문제가
안 됐습니다. 길이 200유닛 이상인 판형에서는 1층 공룡이 7층 몬스터를 최근접으로 집어 들고
그쪽으로 직진합니다.

> 이 문서 초안은 C# 기본값 80을 적었습니다. `CLAUDE.md` 가 세 번 물렸다고 경고하는 바로 그
> 직렬화-기본값 함정에 문서가 다시 걸린 것입니다. **런타임 값을 알고 싶으면 필드 선언이 아니라
> 생성된 애셋을 보세요.**

`UnitRegistry.FindNearestEnemy` 는 팀 리스트를 전수 순회할 뿐 층 개념이 없습니다.

### 1.3 UnitRegistry에 층이 없습니다

`Team` 3개(Red/Blue/Neutral) 키의 static 딕셔너리입니다. "지금 교전 중인 층"을 표현할 자리가
없습니다. 그리고 **static이라 씬 로드보다 오래 삽니다** — 모드 전환 때 `Clear()` 를 빠뜨리면
이전 모드의 유령이 남습니다 (`CLAUDE.md` 에 이미 적힌 함정).

### 1.4 "한 팀 전멸 = 경기 종료" 가 하드코딩

`BattleManager.HandleUnitDied` (`:242`):

```csharp
if (UnitRegistry.AliveCount(Team.Red) > 0 && UnitRegistry.AliveCount(Team.Blue) > 0) return;
awaitingVerdict = true;
```

건틀릿에서 아군 전멸은 **끝이 아니라 다음 웨이브 대기**입니다. 몬스터 쪽도 한 층 비었다고
끝이 아닙니다.

### 1.5 BattlePhase 3개로는 부족합니다

`Placement / Fighting / Finished` (`GameEnums.cs:12`). "전멸했고 다음 무리를 기다리는 중"이
없습니다. **다만 enum에 값을 추가하는 건 위험합니다** — `BattleHUD`, `BattleMusic`,
`BattleCameraDirector`, `VictoryDance` 가 전부 이 값으로 분기하고, 새 값은 어디서도 처리되지
않은 채 조용히 지나갑니다. 설계(3.3)에서 다르게 풀었습니다.

### 1.6 카메라가 원형 아레나를 가정합니다

- `OrbitCameraController.panLimit` — 피벗을 X/Z ±panLimit **정사각형**으로 클램프 (`:161`).
  실제 값은 **24.2**입니다: `BattleSceneBuilder:640` 이 `ArenaRadius * 1.1` 로 씁니다.
  C# 기본값 80이 아닙니다 — 1.2와 같은 함정입니다. 상황은 초안에 적은 것보다 **나쁩니다**:
  24.2로는 판형은커녕 **한 개 층도 가로지르지 못합니다.**
- `BattleCameraDirector.placementDistance = 34` 에서 `FocusOn(Vector3.zero, ...)` — 원점 중심.
- 프레이밍은 양 팀 가중 중심입니다. 건틀릿에서 보고 싶은 건 **선두**지 전체 중심이 아닙니다.

### 1.7 층별 난이도를 넣을 자리가 없습니다

밸런스는 `CreatureDefinition` 에만 있고 스폰 시점에 `CreatureUnit.Initialize()` 를 통해 컴포넌트로
흘러갑니다 (`CLAUDE.md` 의 핵심 규칙). 층별 배율을 넣으려면 **이 관문을 지나야 합니다.**
프리팹이나 씬에 수치를 박는 건 금지입니다.

주의: **방어력은 감산식**입니다 — `Health.TakeDamage` (`:42`) 가 `Mathf.Max(1f, raw - armor)`.
체력과 독립적인 손잡이가 아닙니다. 층 배율로 armor를 올리면 어느 지점에서 갑자기 모든 공격이
1 데미지가 되어 난이도가 선형이 아니라 절벽이 됩니다. **배율은 체력과 공격력에만.**

## 2. 계단을 어떻게 오를 것인가 — 세 가지 안

1.1이 이 모드의 성패입니다. 세 안을 비교합니다.

| 안 | 내용 | 비용 | 위험 |
|---|---|---|---|
| **A. 평면 층 + 완만한 경사로** | 각 층은 평평한 판. 층 사이는 12–15° 경사로. 계단의 "단차"는 옆면 장식으로만 표현 | 낮음 | 경사각 튜닝 필요 |
| B. 실제 단차 + 스텝 오프셋 로직 | `CreatureLocomotion` 에 계단 오르기 추가 (전방 레이 → 턱 감지 → 수직 보정) | 중 | 검증된 로코모션을 건드림. 평지 전투 회귀 위험 |
| C. NavMesh 도입 | `com.unity.ai.navigation`, 로코모션 교체 | 높음 | `Docs/roadmap.md` M4 항목. 전투 AI 전체 재검증 |

### 권고: A안

수평 추진만으로도 **경사로는 올라갑니다** — 경사면의 법선이 수평력을 위로 굴절시키기 때문입니다.
수직 성분이 없다는 1.1의 문제는 *턱*에서만 치명적이지 *비탈*에서는 아닙니다. 접지 레이캐스트도
비탈에서 정상 동작합니다 (아래로 쏘니까).

B안은 지금 잘 도는 로코모션에 손을 대는 것이고, 이 프로젝트는 스태거 하나 넣었다가 보스
승률이 5-7에서 11-1로 뒤집힌 전례가 있습니다. 로코모션은 밸런스에 직결됩니다.

C안은 모드 하나 때문에 치를 값이 아닙니다.

### 하지만 A안도 **가정**입니다 — 제일 먼저 검증하세요

경사각, 마찰, 작은 콜라이더, `ClampMagnitude(change, moveSpeed)` 가 오르막에서 실효 속도를
얼마나 깎는지 — 전부 측정해봐야 압니다. 그래서 구현 순서 1단계가 **"경사로 프로토타입"** 이고,
여기서 실패하면 A안을 버리고 B/C로 갑니다. 모드를 다 만들고 나서 "공룡이 못 올라가네"를
발견하는 것이 이 문서가 막으려는 유일한 최악의 결과입니다.

**검증 기준은 이 문서가 아니라 [`gauntlet-step1-ramp-probe.md`](gauntlet-step1-ramp-probe.md)
에 있습니다.** 초안이 여기 적었던 기준("가장 느리고 가장 작은 공룡 Velociraptor…")은 틀렸습니다:
Velociraptor는 로스터에서 **가장 빠른** 공룡입니다 (Speed 11.0). 가장 느린 것은 Malformed Rex
(4.8, 동시에 가장 무겁고 콜라이더도 가장 큼)이고, 콜라이더가 가장 작은 것이 Velociraptor입니다.

**단일 최악 케이스가 없습니다** — 셋이 서로 다른 실패 모드를 담당합니다. 특히 가장 빠른
개체는 경사로 꼭대기에서 **튀어 오르는** 실패 모드를 가지는데, 이건 "도달 시간"으로 재면
오히려 더 빨리 도착해서 합격으로 채점됩니다. 초안 기준으로는 보이지 않았을 결함입니다.

## 3. 설계

### 3.1 씬 구조 — 두 아레나를 만들고 토글

```
Arena.unity
├── Ground / Boundary / Environment      ← 기존 원형 아레나 (VersusArena 아래로 이동)
├── GauntletArena                        ← 신규, 기본 비활성
│   ├── Tier_00 .. Tier_09               ← 평면 판 + 다음 층으로 가는 경사로
│   │   ├── Platform  (Collider)
│   │   ├── Ramp      (Collider)
│   │   ├── SpawnPoints (몬스터 배치용 Transform 배열)
│   │   └── Objective   (공룡이 이 층에서 향할 지점)
│   └── StartPlatform                    ← 플레이어 공룡 출발 지점
└── HUD
```

**두 아레나를 동시에 만들어 두고 루트만 켜고 끕니다.** 씬 재로드보다 단순하고, 비활성
렌더러는 비용이 0입니다. 정적 배칭에는 양쪽이 다 들어가지만 그건 빌드 시간 문제지 런타임
문제가 아닙니다.

`BattleSceneBuilder` 가 둘 다 생성합니다. **씬을 손으로 고치지 마세요** — 기존 규칙 그대로입니다.
경사로/플랫폼 콜라이더는 `Docs/performance.md` 와 최근 작업에 따라 **그림자를 던지지 않게**
설정하고, `BatchingStatic` 을 켭니다.

주의: 기존 `MarkSceneryStatic` / `StripSceneryShadowCasting` 은 `{ "Ground", "Boundary",
"Environment" }` 루트를 순회합니다. 새 루트를 이 목록에 추가해야 합니다.

### 3.2 데이터 — `GauntletLadder`

층 구성은 코드가 아니라 애셋입니다. `CreatureBlueprints` 와 같은 방식으로 에디터 스크립트가
생성합니다.

```csharp
[System.Serializable]
public class GauntletTierSpec
{
    public string label;                    // "1층", "보스" 등 HUD 표기
    public CreatureDefinition[] species;    // 이 층에 세울 종 (랜덤 배분)
    public int count;                       // 마리 수
    public float healthScale;               // 체력 배율
    public float damageScale;               // 공격력 배율
    public bool isBoss;                     // 마지막 층 연출/음악 전환용
}
```

**`armorScale` 은 없습니다.** 1.7의 이유 — 감산식이라 난이도가 절벽이 됩니다.

기본 사다리 (초안, 6단계에서 측정 후 조정):

| 층 | 마리 | 체력 × | 공격 × | 구성 |
|---|---|---|---|---|
| 1 | 3 | 1.0 | 1.0 | 약한 종만 |
| 2 | 4 | 1.1 | 1.0 | |
| 3 | 5 | 1.2 | 1.05 | 중형 섞기 시작 |
| 4 | 5 | 1.35 | 1.1 | |
| 5 | 6 | 1.5 | 1.15 | |
| 6 | 7 | 1.7 | 1.2 | |
| 7 | 8 | 1.9 | 1.25 | 대형 섞기 시작 |
| 8 | 9 | 2.1 | 1.3 | |
| 9 | 10 | 2.4 | 1.4 | |
| 10 | 1 | — | — | **보스** (`CreatureBlueprints` 의 기존 보스 재사용) |

**두 손잡이를 같이 씁니다.** 마릿수만 늘리면 후반이 난전 관리가 되고, 배율만 올리면 같은 그림이
숫자만 커집니다. 마릿수 3→10과 체력 1.0→2.4를 겹치면 초반은 정찰전, 후반은 물량전으로 성격이
바뀝니다.

체력을 공격력보다 훨씬 빠르게(2.4배 vs 1.4배) 올리는 이유: 공격력 스케일링은 플레이어 공룡을
**즉사**시켜 체감이 "어렵다"가 아니라 "불공정하다"가 됩니다. 체력 스케일링은 전투를 길게 만들
뿐입니다. 보스 밸런싱에서 이미 확인된 것 — 승률을 예측하는 지표는 체력이 아니라 TTK였습니다.

**동시 등장 마릿수 확인**: 최대는 9층의 10마리 + 아군 약 10마리 = **20마리**. `Docs/performance.md`
가 측정한 현재 상한(24마리)과 같은 범위이므로 O(n²) 근접 스캔의 트리거를 당기지 않습니다.
사다리를 위로 늘릴 때는 그 문서의 트리거를 먼저 확인하세요.

### 3.3 상태 — `BattlePhase`는 건드리지 않습니다

1.5의 이유로 공용 enum에 값을 추가하지 않습니다. 대신:

```csharp
public enum GameMode { Versus, Gauntlet }

public enum GauntletState
{
    Ready,        // 배치 화면. 출발 대기
    Advancing,    // 공룡이 다음 층으로 이동 중 (교전 없음)
    Engaging,     // 현재 층 몬스터와 교전 중
    WaveWiped,    // 아군 전멸. "더 보내기" 버튼 대기
    Cleared,      // 보스 격파
    Defeated      // 예산 소진 + 전멸
}
```

- `BattleManager` 에 `GameMode Mode { get; }` 추가.
- 건틀릿 실행 중 `BattlePhase` 는 계속 `Fighting` 입니다. 기존 HUD/음악/카메라/춤은 **전부 그대로
  동작합니다** — 이게 enum을 안 건드리는 이유입니다.
- `BattleManager.HandleUnitDied` 에 한 줄: `if (Mode == GameMode.Gauntlet) { gauntlet.OnUnitDied(unit); return; }`
- `GauntletDirector` (신규 MonoBehaviour)가 `GauntletState` 를 소유하고, `StateChanged`,
  `TierChanged`, `RunEnded` 이벤트를 냅니다. **폴링 금지** — 기존 이벤트 규약 그대로.

### 3.4 타게팅 — 층을 안 지나간 몬스터는 등록조차 안 합니다

1.2를 코드 수정 없이 푸는 방법입니다.

`CreatureUnit` 은 `OnEnable` 에서 `UnitRegistry` 에 등록합니다. 따라서:

- 모든 층의 몬스터를 런 시작 시 미리 스폰하되 **`SetActive(false)`** 로 둡니다.
  → 레지스트리에 없으므로 `FindNearestEnemy` 가 절대 찾지 못합니다. **타게팅 코드 수정 0줄.**
- 공룡 선두가 N층 진입 트리거를 밟으면 N층 몬스터만 `SetActive(true)`.
- 미리 스폰하는 이유: 전투 중 인스턴스화는 프레임을 튀게 합니다. 비활성 오브젝트는 Update도
  렌더도 안 돕니다.

**대안 검토**: `FindNearestEnemy` 에 층 필터를 추가하는 방법도 있지만, 모든 호출자와
`SteeringBehaviors.Separation`, 카메라 프레이밍까지 층을 알아야 해서 번집니다. 비활성 스폰은
기존 생명주기를 그대로 쓰므로 새로운 규칙이 없습니다.

### 3.5 진격 — 적이 없을 때 공룡은 무엇을 하는가

지금 `CreatureBrain` 은 적이 없으면 `Idle` 로 서 있습니다. 건틀릿에서는 다음 층으로 걸어가야
합니다.

```csharp
// CreatureBrain
public Vector3? MarchTarget { get; set; }   // null이면 기존 동작 그대로
```

- `Idle` 상태에서 `MarchTarget` 이 있으면 그쪽으로 `Seek`.
- `GauntletDirector` 가 층이 바뀔 때마다 아군 전원의 `MarchTarget` 을 다음 층의 `Objective` 로
  설정.
- 적을 찾으면 기존 로직이 이깁니다 — 진격은 **대체가 아니라 폴백**입니다.
- 기존 **타깃 유지** 규칙(현재 타깃이 죽을 때까지 교체 안 함)은 그대로 둡니다. 이유는
  `CLAUDE.md` 에 있고 건틀릿에서도 유효합니다.

`MarchTarget` 이 nullable이라 대전 모드는 완전히 무영향입니다.

### 3.6 스탯 배율 — Initialize 관문을 통과시킵니다

1.7의 규칙을 지키는 유일한 방법:

```csharp
public void Initialize(CreatureDefinition definition, Team team, Color teamColor,
                       float healthScale = 1f, float damageScale = 1f)
```

- 기본 인자라 **기존 호출부 전부 무수정**.
- `Health.Configure(definition.maxHealth * healthScale, definition.armor)` — armor는 배율 없음.
- `MeleeAttack.Configure(definition, damageScale)`.
- 프리팹과 ScriptableObject는 손대지 않습니다. 배율은 스폰 시점에만 존재합니다.

`CreatureSpawner.Spawn` 에도 같은 형태로 선택 인자를 추가합니다.

### 3.7 카메라

- `OrbitCameraController.panLimit` 을 **단일 값에서 사각 경계로**: `panBoundsMin/Max` (Vector2).
  원형 아레나는 `(-80,-80)..(80,80)`, 건틀릿은 판형 실측치. `ClampToArena` 만 고치면 됩니다.
- `BattleCameraDirector` 에 건틀릿 프레이밍 추가: 중심은 **아군 선두 무리**(진행 방향 최전방
  70% 지점), 반경은 기존 `CoveringRadius` 재사용.
- 배치 화면: `FocusOn(Vector3.zero, placementDistance)` 대신 `StartPlatform` 을 봅니다.
- 보스 층 진입 시 한 번 넓게 빼서 보스를 보여주는 연출은 **v1 범위 밖**. 목록에만 둡니다.

**배치 화면 상단에 모드 토글.** 현재 `PlacementPanel` 은 화면 하단 y 0–0.16입니다

### 3.9 경제 — **결정 필요** (5번 참고)

"모든 공룡이 죽었으면 버튼을 눌러서 추가 공룡들을 출발시킬 수 있음" 에서 **횟수 제한이

`BattleLoadout` 의 팀당 예산 개념을 그대로 재사용할 수 있습니다.

잡습니다 (회귀 주입으로 확인).

## 3.11 스톨 — 이 모드의 유일한 치명적 버그 유형 (2026-07-29)

플레이 보고: **"4였나 5부터 적이 안나타남"**, 그리고 그 전의 **"4층까지 왔는데 다 죽었는데도
아무 버튼도 안나오고"**. 같은 뿌리입니다.

`GauntletDirector` 는 죽음 이벤트로 굴러가는 상태 기계입니다. 지금까지 나온 스톨 세 건이
전부 같은 모양이었습니다 — **한 순간에 알아채야만 하는 전이**, 그 순간을 놓치는 평범한 경합,
그리고 빠져나올 길도 메시지도 없는 상태.

이번 것은 "이 층은 소탕됐다" 였습니다. 판정이 `HandleMonsterDied` 안의 `State != Engaging`
가드 뒤에만 있었기 때문에:

1. 아군 마지막 한 마리와 몬스터 마지막 한 마리가 **같은 프레임에** 죽습니다 (동귀어진 — 층이
   올라갈수록 흔해집니다. 4~5층부터 보고된 이유입니다)
2. 아군의 `Died` 가 먼저 발화하면 → `WaveWiped`
3. 이어서 몬스터의 `Died` 가 가드에 걸려 **return**. 층은 비었는데 아무도 기록하지 않음
4. 플레이어가 더 보냅니다 → 그 층으로 진격 → `WakeTier` 가 **시체를 깨운 것으로 세고**
   `Engaging` 선언
5. `Engaging` 에는 더 보내기 버튼이 없고, 기다리는 죽음은 이미 전부 일어났습니다. **끝.**

고친 방식은 이벤트를 하나 더 거는 게 아니라 **조건을 폴링으로 바꾸는 것**입니다:

- `CheckTierCleared()` 를 `Update` 에서도 호출 — **참일 수 있는 때마다 검사하는 조건은 놓칠
  수 없습니다.** 몬스터 10마리 리스트를 프레임당 한 번 훑는 비용
- `WakeTier` 는 `IsDead` 를 세지 않습니다 — 시체는 12초 남습니다 (`corpseLifetime`).
  **시체는 수비병이 아닙니다**
- `CheckTierCleared` 의 `advanceTimer > 0` 가드는 필수입니다. 없으면 폴링이 매 프레임 타이머를
  되감아 영원히 만료되지 않습니다

떨어짐도 같은 스톨을 다른 문으로 만들어냅니다. **판 밖으로 떨어진 개체는 무한히 살아 있고**,
"이 웨이브 끝났나"의 판정은 `AnyAlive` 입니다. 한 마리만 넘어가도 진격도 전멸도 영원히
성립하지 않습니다. 두 겹으로 막습니다 — 판 네 면 전부에 보이지 않는 벽 (`Wall_Back` /
`Wall_Front` 추가. 옆면만 있었고 **양 끝이 뚫려 있었습니다**), 그리고 `RescueTheFallen()` 이
y < -8 인 개체를 원위치로 되돌립니다. 죽이지 않고 되돌리는 이유는, 플레이어는 그게 떨어지는
걸 보지도 못했기 때문입니다.

**회귀 방지**: `GauntletRunProbe`. 8배속으로 한 판을 끝까지 돌립니다. 밸런스는 보지 않습니다 —
오직 "런이 계속 움직이는가" 만 봅니다. 메뉴 두 개, 헤드리스 진입점 두 개:

```bash
Unity.exe -batchmode -projectPath <project> \
          -executeMethod DinoBattle.EditorTools.GauntletRunProbe.RunHeadless          # 즉시 증원
Unity.exe -batchmode -projectPath <project> \
          -executeMethod DinoBattle.EditorTools.GauntletRunProbe.RunHeadlessPatient   # 전멸 후에만
```

**`Patient` 쪽이 이 버그를 잡는 쪽입니다.** 이 프로브를 만들면서 두 번 헛짚었고, 둘 다
"통과했으니 고쳐졌다" 로 갈 뻔했습니다:

1. **첫 판정 기준이 틀렸습니다.** "진전 없음"을 스톨로 봤는데, 더 보내기 버튼이 눌리는 것을
   진전으로 셌습니다. 3.12의 전투 중 증원이 그걸 **항상 참**으로 만들기 때문에, 빈 층에 계속
   증원을 들이붓는 교착 상태가 이 테스트에는 건강한 런과 똑같아 보였습니다. 지금은 교착의
   서명을 직접 단언합니다 — **`Engaging` 인데 `DefendersAlive == 0`** 이 6초 지속되면 실패
2. **판정을 고쳤는데도 통과했습니다.** 프로브가 쿨다운마다 증원해서 웨이브가 전멸하는 일이
   거의 없었고, 그러면 `WaveWiped` 를 지나가지 않으므로 **경합이 일어날 기회 자체가 없었습니다.**
   `Patient` 모드는 전멸했을 때만 보냅니다 — 이 모드가 생기기 전 플레이 방식이자, 사용자가
   버그를 만난 조건입니다

버그를 되심은 상태로 `Patient` 를 돌리면 **5층에서 DEADLOCK** 으로 실패합니다 — 보고된
"4였나 5부터" 와 같은 자리입니다. 고친 상태에서는 그 지점을 통과합니다. **회귀를 주입해
실패하는 것을 보기 전까지, 통과는 아무것도 증명하지 않습니다.**

프로브는 **멈춤(STALL)과 벽(WALL)을 구분합니다.** 웨이브가 계속 소모되고 있으면 기계는 정상이고
플레이어가 계속 지고 있는 것 — 그건 `GauntletLadder` 의 숫자 문제지 `GauntletDirector` 의
결함이 아닙니다. 설계 결정 때문에 빨간불이 뜨는 검사는 아무도 안 돌리게 됩니다.

## 6.1 밸런스 측정 결과 (2026-07-29) — 6단계 첫 실측

이제껏 사다리(3→10마리, 체력 ×1.0→×2.4)는 **한 번도 측정된 적이 없는 초안**이었습니다.
프로브가 처음으로 숫자를 냈습니다:

| 플레이 방식 | 결과 |
|---|---|
| 쿨다운마다 증원 (3.12 기능 사용) | **10층 전부 클리어**, 총 35웨이브 |
| 전멸했을 때만 증원 (기능 없이) | **8~9층에서 벽** (2회 실행: 9층 93웨이브 / 8층 24웨이브) |

벽에서는 웨이브가 `Engaging` 에 도달하지도 못합니다 — 이전 층 목표점에 스폰되는 순간 다음 층
몬스터 9~10마리(aggroRange 90, 층 간격 31)가 곧장 달려와 3~7초 만에 쓸어버립니다. **한 번에
5마리씩 밀어 넣는 방식으로는 이길 수 없는 층입니다.**

전멸-only 경로의 층당 상태 전이 횟수: 2, 2, 5, 7, 8, 15, 29, 51, 81 — 6층부터 층마다 거의
두 배가 됩니다. 곡선이 아니라 지수입니다.

즉 **지금 사다리는 전투 중 증원을 전제로만 넘어갑니다.** 그 기능이 난이도 곡선의 일부가 된
셈인데, 나쁜 결과는 아닙니다 — 대신 다음 중 하나는 결정이 필요합니다:

- 그대로 둔다 (증원이 핵심 기술이 됨). 단 9층은 여전히 급격한 절벽입니다
- 8~9층 마릿수/체력 배율을 낮춘다
- 증원 쿨다운(6초)을 줄인다

`Docs/gauntlet-mode.md` 6단계는 이제 "측정 안 됨" 이 아니라 "측정됨, 조정 대기" 입니다.

`-quit` 를 주지 않는 것이 중요합니다 — 플레이 모드는 에디터 루프가 계속 돌아야 하고, 프로브가
판정을 종료 코드로 실어 직접 프로세스를 끝냅니다. 그리고 **플레이 모드 진입은 도메인 리로드**라
`EditorApplication.update` 구독과 static이 전부 날아갑니다. 첫 시도가 플레이 모드에 들어간 채로
영원히 멈춰 있던 이유입니다 — `SessionState` + `[InitializeOnLoadMethod]` 로 리로드 건너편에서
다시 붙습니다.

## 3.12 전투 중 증원 (2026-07-29)

요청: **"싸우는 중에도 추가로 공룡을 투입할 수 있도록"**. 원래는 `WaveWiped` 에서만
가능했습니다.

- `CanSendWave` 에 두 번째 경로: `Advancing`/`Engaging` + 쿨다운 6초
- 전멸했을 때는 **쿨다운 없음**. 이미 진 판을 다시 시작하는 데 기다리게 할 이유가 없습니다
- 쿨다운은 밸런스만의 문제가 아닙니다 — `Docs/performance.md` 의 동시 24마리 천장을 버튼
  연타로 몇 초 만에 넘깁니다
- **증원은 웨이브를 새로 시작하지 않습니다**: `wave` 를 비우지 않고 `OrderAdvance()` 도 부르지
  않습니다. 불렀다면 이미 교전 중인 개체 전원이 진격 명령을 받아 **싸우다 말고 걸어가버립니다**.
  새로 도착한 개체에게만 현재 층 목표를 줍니다
- 버튼은 이제 전투 내내 떠 있고 쿨다운 중에는 회색 + 남은 초를 표시합니다. 누를 때마다 6초씩
  사라지는 버튼은 충전 중이 아니라 고장난 것처럼 보입니다

## 3.13 영웅, 보스의 부하, 그리고 클리어 연출 (2026-07-29)

### 영웅 공룡

증원 쿨다운을 6초 → **3초**로 줄이고, 별도 버튼으로 **영웅 공룡**을 10초마다 보낼 수 있게
했습니다. 영웅은 **황금색이고 20% 큽니다** (`CreatureUnit.MarkAsHero`).

- 로스터는 `Roster_Default` — 영웅은 "영웅 공룡"이지 보스가 아닙니다
- **상위 절반(비용 기준)에서만** 뽑습니다. 전체에서 뽑으면 10초 기다린 보상이 황금색
  벨로시랩터로 나오는 일이 자주 생깁니다
- 연속 중복 금지. 같은 게 두 번 나오면 분포와 무관하게 "랜덤이 고장났다"로 읽힙니다
- 색은 **알베도를 90% 가까이 금색으로 덮습니다.** 셰이더가 라이팅을 받으므로 명암은 그대로
  남습니다 — 0.85로 했더니 초록 공룡이 **황록색**이 되어 금색으로 안 보였습니다
- 크기·색만으로는 아무 효과가 없습니다 (사거리·질량은 definition 값). 체력 ×2.5 / 공격 ×1.6을
  같이 겁니다

**쿨다운은 두 개가 독립입니다.** 영웅을 썼다고 증원이 밀리거나 그 반대가 되면 선택이 아니라
하나의 자원이 됩니다.

### 동시 개체 수 상한 — 쿨다운만으로는 부족합니다

3초 쿨다운으로 프로브를 돌렸더니 보스 층에서 **100마리가 넘게** 쌓였습니다. `Docs/performance.md`
의 측정 천장은 동시 24마리입니다.

**쿨다운은 비율을 제한하지 총량을 제한하지 않습니다.** 아무것도 개체를 줄이지 않으니 계속
누적됩니다. 그래서 `waveLimit = 20` — 아군 생존 수가 20이면 버튼이 죽고, 죽어야 다시 살아납니다.
버튼 라벨이 `가득` / `N초` 로 갈리는 이유입니다: 하나는 기다리면 풀리고 하나는 죽어야 풀립니다.

프로브가 이제 `peak N creatures on the board` 를 매 실행 기록합니다 — 스크린샷으로 눈대중할
숫자가 아닙니다.

### 보스의 부하 거미

보스(Megarachne)가 주기적으로 **부하 거미를 최대 5마리**까지 소환합니다. 보스 자신의 종을
0.42배로 줄인 것이라 새 애셋이 필요 없고, 누가 소환했는지 한눈에 보입니다.

- **`tierMonsters` 에 넣지 않습니다.** 그 리스트가 "이 층 소탕됨"의 판정이라, 부하를 넣으면
  보스를 잡고도 마지막 거미까지 청소해야 런이 끝납니다. **보스를 죽이면 이깁니다.** 부하는 같이
  사라집니다
- **매 주기마다 상한까지 채웁니다.** 한 마리씩 추가하는 방식으로 처음 측정했더니 보스전이 약
  14초인데 거미 수명이 소환 간격보다 짧아 **동시 1마리**가 최대였습니다 — "최대 5마리"가 아무도
  못 보는 숫자가 됩니다. 채우는 방식이라야 5가 실제로 화면에 보이는 수입니다
- 간격 5초. 7초로는 14초짜리 싸움에서 한 번밖에 안 터집니다

### 클리어 연출

보스를 잡으면 `BattleManager.DeclareGauntletCleared()` 가 **대전 모드와 같은 문으로** 결과를
통보합니다 — `Winner = Red`, `Phase = Finished`, `BattleEnded`.

건틀릿은 첫 웨이브부터 보스까지 `Fighting` 을 유지하는데, 축하하는 쪽(`VictoryDance`,
`VictoryCelebration`, 결과 패널, 음악)은 전부 `Finished` 를 기다립니다. 그래서 보스를 잡아도
**그냥 멈췄습니다.** 각 시스템에 건틀릿을 가르치는 대신 런이 같은 문으로 신고하게 했으므로,
`VictoryDance` 는 이 모드의 존재를 여전히 몰라도 됩니다.

`DeclareResult` 는 재사용할 수 없습니다 — 머릿수로 승자를 정하고 `activeUnits` 로 정리하는데,
건틀릿은 그 리스트를 채우지 않습니다(디렉터가 개체를 소유). 여기서는 승자가 이미 정해져 있고
정리는 레지스트리로 합니다.

## 4. 구현 순서

각 단계는 **검증 기준을 통과해야** 다음으로 갑니다. 특히 1단계.

### 1단계 — 경사로 프로브 (게이트) ✅ 통과

**측정 완료 (2026-07-26). → [`gauntlet-step1-ramp-probe.md`](gauntlet-step1-ramp-probe.md) 14절**

**A안 채택.** 8°–25° 전 구간에서 세 종 각 5시행, **75/75 도달, 후퇴 0, 정체 0**, 시간비 최대
1.077. 등반 비용은 사실상 없습니다. B안(스텝 오프셋)도 C안(NavMesh)도 필요 없습니다.

2단계로 넘어가는 확정 제약 둘:

- **경사각 12°** 권고 (15°까지 안전, 20–25°는 크레스트 체공 지표 재정비 후 판정)
- **판 위 모든 이음매·연석의 단차는 0.15유닛 미만.** 실측 임계는 콜라이더 반지름과 일치했고
  (랩터 0.2에서 이미 실패), 이 문서 1.1이 추측한 "0.3유닛"보다 **두 배 엄격**합니다

12°/H=2면 램프 하나가 수평 9.4유닛, 10층 판 길이는 약 290유닛입니다. `panLimit` 이 24.2이므로
(1.6) 카메라는 2단계에서 **반드시** 같이 고쳐야 합니다.

모드도 UI도 없이, 경사로만 있는 코스에서 공룡을 걷게 하고 **가설을 죽이려고 시도합니다.**
합격 기준, 대조군, 잡아야 할 실패 모드 9종, 계측 방법, 시행 횟수, 판정 규칙이 그 문서에
있습니다.

그 문서가 초안과 다르게 잡은 것 중 중요한 둘:

- **경사각 θ는 상수가 아니라 프로브의 출력입니다.** 8/12/15/20/25°를 "확인"하는 게 아니라
  통과하는 최대 각을 찾고, 거기서 여유를 뺀 값을 2단계 지오메트리에 넘깁니다.
- **도달 시간은 게이트가 아니라 경보입니다.** 시간만 보면 꼭대기에서 튀어 오르는 개체가
  "더 빨리 도착"해 합격합니다. 게이트는 단조 진행과 조향 권한 유지입니다.

**실패 시**: A안 폐기, B안(스텝 오프셋) 또는 C안(NavMesh)으로. 판정 규칙과 부분 통과의 의미는
그 문서 9절.

### 2단계 — 아레나 지오메트리

`BattleSceneBuilder` 에 `GauntletArena` 생성. 1단계에서 나온 경사각을 상수로.
`MarkSceneryStatic` / `StripSceneryShadowCasting` 루트 목록에 추가.
**검증**: `check-project.sh` 통과, 그림자 캐스터 수가 늘지 않을 것, 아레나 안에 떠도는 콜라이더
없을 것 (기존 `AssertArenaClear` 재사용).

### 3단계 — 데이터 + 스폰

`GauntletLadder` 애셋 생성기, `Initialize` 배율 인자, 비활성 선스폰.
**검증**: 10층 전부 스폰되고 레지스트리에는 0마리 (전부 비활성), 층 활성화 시 정확히 그 층만
등록될 것.

### 4단계 — 진행 로직

`GauntletDirector`, `MarchTarget`, 층 진입 트리거, `WaveWiped` / 더 보내기.
**검증**: 한 판을 끝까지 자동 진행 (스크립트로 아군을 무적으로 만들고) — 10층 전부 순서대로
활성화되고 보스에서 `Cleared`.

### 5단계 — 카메라 + UI

`panBounds`, 선두 프레이밍, 모드 토글, 층/예산 HUD.
**검증**: 모드 전환을 5회 왕복해도 `UnitRegistry` 에 유령이 없을 것 (1.3).

### 6단계 — 밸런싱 (1차 실측 완료, 조정 대기 — **6.1 참고**)

`GauntletRunProbe` 가 첫 숫자를 냈습니다: 증원 사용 시 10층 클리어(35웨이브), 미사용 시 **9층
벽**(93웨이브). 아직 1회씩이므로 분포가 아니라 신호입니다.

다회 실행으로 층별 도달률 분포를 뽑는 것은 남아 있습니다.
**검증 기준 제안**: 표준 편성으로 6–8층 도달이 중앙값. 보스 클리어율 20–30%.

> 보스 밸런싱에서 배운 것: **±25%p 안쪽 변화는 노이즈입니다.** 한 층을 만졌는데 다른 층이
> 같이 움직이면 그건 튜닝이 아니라 우연입니다. 시행 횟수를 먼저 늘리세요.

## 5. 결정이 필요한 것

1. ~~"각 계단은 10개"의 해석~~ — **해결됨**: 계단 총 10개, 층별 마릿수는 곡선 (0절, 3.2).
2. **추가 출발 횟수** — 3.9의 총예산 방식으로 갈까요, 무제한(연습 모드 성격)일까요?
   무제한이면 실패가 불가능해 긴장이 사라집니다.
3. **아군이 층을 넘어가는 조건** — 그 층 몬스터 전멸인가요, 아니면 살아남은 놈을 두고 지나갈
   수 있나요? (전멸을 기본으로 잡았습니다)
4. **죽은 아군의 처리** — 다음 웨이브에 부활 없음이 기본입니다. 진행 상황(도달 층)은 유지합니다.
5. **보스 층 도달 시 회복** — 없음이 기본. 있으면 난이도 곡선이 완전히 달라집니다.

2–5번은 **4단계(진행 로직) 전까지만** 정하면 됩니다. 1–3단계는 이 답들과 무관하게 진행할 수
있습니다.
