# 성능 — 알고 있지만 지금은 고치지 않는 것

여기 적힌 두 항목은 **실재하는 결함이고, 지금 고치면 손해**입니다. 코드 리뷰에서 나왔지만
측정해보니 현재 규모에서 비용이 0에 가까웠고, 고치면 코드만 복잡해집니다.

문서로 남기는 이유는 하나입니다 — **언제 다시 봐야 하는지**를 지금 적어두지 않으면, 다음에
이 코드를 보는 사람(대개 6개월 뒤의 나)이 처음부터 다시 재야 하기 때문입니다.

각 항목은 **트리거**를 갖습니다. 트리거가 당겨지기 전에는 손대지 마세요.

---

## 전제 — 필드에 설 수 있는 공룡은 최대 24마리입니다

두 항목 다 O(n²)이므로 n이 전부입니다. 그리고 n은 생각보다 훨씬 작습니다:

| 제약 | 값 | 출처 |
|---|---|---|
| 팀당 예산 | 1000 | `BattleManager.budgetPerTeam` |
| 가장 싼 공룡 | 90 (Velociraptor) | `CreatureBlueprints.cs:259` |
| → 수동 배치 상한 | 팀당 11 | 1000 ÷ 90 |
| 자동 배치 상한 | 팀당 12 | `AutoPlacer.maxPerTeam` |
| **필드 총원 최대** | **24** | |

리뷰 초안은 "100 대 100"을 가정하고 이 두 항목의 심각도를 매겼는데, **게임이 도달할 수 없는
숫자**였습니다. 24마리에서 다시 계산한 것이 아래입니다.

## P1 — 매 프레임 O(n²) 근접 스캔 (분리 조향 + 충돌 감지)

### 무엇

생존 공룡 목록을 개체마다 전부 훑는 루프가 두 군데 있습니다. 둘 다 공간 분할 없이 전수 검사입니다.

| 위치 | 주기 | n=24일 때 초당 거리 검사 |
|---|---|---|
| `SteeringBehaviors.Separation` (`:100`) ← `CreatureBrain.TickCombat` (`:317`), **Update** | 매 프레임 (60Hz) | **34,560** |
| `CreatureImpact.ScanTeam` (`:105`) | 0.06초마다 (16.7Hz) | **9,600** |

**리뷰에서 제가 지목한 건 `CreatureImpact` 쪽이었는데, 실제로 비싼 쪽은 분리 조향입니다** —
프레임마다 돌기 때문에 3.6배 더 나갑니다. 브로드페이즈를 넣을 일이 생기면 **분리 조향부터**
연결하세요. 충돌 감지만 고치면 비용의 22%를 잡고 끝납니다.

### 왜 지금 고치지 않는가

초당 44,000회의 `Vector3` 뺄셈과 `sqrMagnitude` 비교입니다. 제곱거리 비교라 `sqrt`도 없습니다.
스냅드래곤급 모바일 코어에서 **1 ms 미만**, 60fps 프레임 예산 16.7 ms의 6% 미만입니다.
이걸 잡으려고 공간 해시를 넣으면 다음이 따라옵니다:

- 매 틱 그리드 재구축 (셀 배열 재사용, 이사 감지, 셀 크기 튜닝)
- 새로운 상태 동기화 지점 — 스폰/사망/디스폰마다 그리드 갱신. `UnitRegistry` 가 static이라
  씬 로드보다 오래 사는 문제(`CLAUDE.md` 참고)를 그리드에도 그대로 물려줍니다
- n=24에서는 **오히려 느려질 가능성이 높습니다**. 24개짜리 선형 스캔은 캐시에 통째로 들어갑니다

### 트리거 — 아래 중 하나라도 참이면 착수

- [ ] `budgetPerTeam` 이 3000을 넘거나 `AutoPlacer.maxPerTeam` 이 40을 넘음
- [ ] 저가 유닛(현재 90 코스트 랩터) 밑으로 더 싼 "떼거리" 유닛이 추가됨
- [ ] 실제 기기 프로파일에서 `CreatureBrain.Update` 가 프레임의 15%를 넘음

n=100이면 분리 조향만 초당 600,000회로 17배가 됩니다. 그때는 확실히 값어치를 합니다.

### 착수하게 되면 — 계획

1. **먼저 측정.** 추측 금지. `ProfilerMarker` 를 `SteeringBehaviors.Separation` 과
   `CreatureImpact.ScanTeam` 에 하나씩 박고 실기기에서 읽으세요. 이 프로젝트에서 추측으로 튜닝했다가
   노이즈를 쫓은 전례가 있습니다 (`CLAUDE.md` 의 보스 밸런스 ±25pp 항목).
2. **`UnitRegistry` 에 균일 그리드를 하나만** 둡니다. 소비자마다 만들지 마세요 — 분리 조향, 충돌
   감지, `FindNearestEnemy` 가 전부 같은 질의("반경 r 안의 생존 유닛")를 합니다. 하나를 공유해야
   갱신 지점도 하나로 남습니다.
3. **셀 크기는 최대 `footprintRadius` 의 2배.** 그러면 어떤 질의든 3×3 셀로 끝납니다.
4. **재구축은 프레임당 한 번**, 소비자별이 아니라 `UnitRegistry` 가 자기 시각에 합니다.
   이동체가 24~200개면 매 프레임 전체 재구축이 증분 갱신보다 싸고 훨씬 덜 틀립니다.
5. **검증은 그리드 없는 경로와 대조.** 같은 프레임에서 전수 검사 결과와 그리드 결과가 같은
   집합을 내는지 확인하는 임시 assert를 켜고 한 판 돌리세요. 브로드페이즈 버그는 조용히
   "가끔 이웃을 놓치는" 형태로 나타나고, 그건 AI가 이상해 보이는 것으로만 드러납니다.

`Docs/roadmap.md` 의 ECS/Job System 항목(공룡 50마리 이상)과 같은 트리거를 공유합니다.
50마리가 필요해지면 둘 중 무엇을 할지 그때 같이 판단하세요 — **그리드가 거의 항상 먼저입니다.**
ECS는 아키텍처 전환이고 그리드는 자료구조 하나입니다.

## P2 — `new[] { Team.Red, Team.Blue }` 프레임당 할당

### 무엇

```csharp
foreach (Team team in new[] { Team.Red, Team.Blue })   // 40바이트, 매 호출
```

두 군데입니다:

| 위치 | 호출 빈도 | 실제 영향 |
|---|---|---|
| `BattleCameraDirector.ChooseVictor` (`:265`) | **무승부일 때 매 LateUpdate** | 초당 ~2.4 KB |
| `CreatureFocusPicker.FindCreatureAt` (`:149`) | 탭당 1회 | 무시 가능 |

카메라 쪽만 문제입니다. 무승부면 `ChooseVictor()` 가 계속 null을 반환해서 `victor` 가 채워지지
않고, `FrameVictor()` 가 매 프레임 다시 호출합니다. 결과 화면이 떠 있는 내내 60Hz로 쓰레기가
쌓입니다.

### 왜 지금 고치지 않는가

`static readonly Team[]` 하나면 끝나는 3줄짜리라, 안 고치는 게 오히려 이상해 보입니다.
그래도 미룬 이유:

- **무승부는 드뭅니다.** 8판 보스 프로브에서 1번 나왔고, 그것도 `verdictGrace` 를 넣은 뒤에야
  처음 관측됐습니다
- 초당 2.4 KB는 모바일 Gen0 GC를 **몇 분에 한 번** 트리거하는 양이고, 그 시점의 화면은 결과
  패널입니다 — 프레임 히치가 가장 안 보이는 순간
- 진짜 문제는 할당이 아니라 **무승부일 때 `ChooseVictor()` 가 매 프레임 재실행된다는 것**입니다.
  배열만 static으로 빼면 증상만 가려지고, 아무 결과도 못 내는 전체 순회는 그대로 남습니다

### 트리거

- [ ] 다른 곳에서도 같은 패턴이 나와서 3곳 이상이 됨 → 한 번에 쓸고 `check-project.sh` 에 규칙 추가
- [ ] 결과 화면에 애니메이션 UI가 붙어서 GC 히치가 보이게 됨

### 착수하게 되면 — 계획

배열을 static으로 빼는 건 **두 번째로** 하세요. 먼저 고칠 것은 원인입니다:

1. `FrameVictor()` 에서 무승부를 **한 번만 판정하고 기억**합니다. 지금은 `victor == null` 이
   "아직 안 골랐음"과 "고를 게 없음"을 둘 다 의미해서 매 프레임 재시도합니다. 둘을 구분하는
   `victorResolved` 플래그 하나면 순회 자체가 사라지고, 할당도 같이 사라집니다.
2. 그 다음에 `Team.Red/Blue` 배열을 `UnitRegistry` 의 `static readonly Team[] Sides` 로 올려
   두 호출처가 공유하게 합니다. `Team` enum에 `Neutral` 이 있어서 `Enum.GetValues` 는 쓸 수
   없습니다 — 명시적 배열이어야 합니다.

## 부작용 기록 — 스파이럴 가드가 오프라인 프로브를 느리게 만들었습니다

`MobilePerformance.ApplyCatchUpCap()` 이 `maximumDeltaTime` 을 `timeScale` 로 나누게 되면서
프레임당 물리 스텝이 어떤 배속에서도 4로 고정됩니다. 플레이어를 위해서는 맞는 동작입니다.

**하지만 에디터 프로브에는 손해입니다.** `BossBalanceProbe.Speed = 16` 은 이제 16배가 아닙니다:

| | maximumDeltaTime | 스텝/프레임 | 60fps 실효 배속 |
|---|---|---|---|
| 변경 전 | 0.0800 | 13.3 | **16.0×** |
| 변경 후 | 0.0050 | 4.0 | **4.8×** |

밸런스 측정이 **3.3배 느려졌습니다.** 결과가 틀리지는 않습니다 — 시뮬레이션은 그대로고 벽시계만
느려집니다. 다만 상수 이름이 거짓말이 됐고, 시행 횟수를 늘려야 하는 밸런싱에서 3.3배는 큽니다.

**고칠 때**: `MobilePerformance` 가 `maximumCatchUpSteps` 를 런타임에 올릴 수 있게 열고,
오프라인 프로브가 시작할 때 올렸다가 끝나며 되돌립니다. 히치로부터 보호할 플레이어가 없는
상황이므로 프로브가 스스로 예외를 선언하는 것이 맞습니다. 배속을 상수로 믿지 말고 **실측
스텝/프레임을 로그로 남기게** 같이 바꾸세요 — 이 항목이 조용히 생긴 이유가 그것입니다.

관련: [`gauntlet-step1-ramp-probe.md`](gauntlet-step1-ramp-probe.md) 0.5절이 같은 사실을
경사로 프로브 쪽에서 다룹니다.

## 이 문서를 갱신하는 규칙

- 트리거를 당겨서 고쳤으면 **항목을 지우고** 커밋 메시지에 측정값을 남기세요
- 새로 미루기로 한 성능 항목은 **반드시 트리거와 함께** 여기 추가하세요. 트리거 없는 항목은
  "나중에"라는 뜻이고, 그건 "안 함"의 다른 말입니다
- 숫자를 적을 때는 **어떻게 쟀는지** 같이 적으세요. 위의 24마리 상한은 예산과 코스트에서
  나온 것이고, 그 둘이 바뀌면 이 문서 전체가 틀립니다
